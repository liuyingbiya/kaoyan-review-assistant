# 面试讲解稿 · 考研复习助手

> 这份是"你要能讲清楚"的底稿。面试官问项目时，按这里的四层往下答。

---

## 第 0 层：一句话说清这是什么

> 「一个按科目组织的考研复习问答工具。我把各科资料按科目导进去，提问时先在**当前科目**的资料里检索最相关的几段，再让大模型基于这几段回答，并把它引用的原文一起返回，可以点开核对。目的是复习时能快速查到一个知识点，而不是翻笔记或者问到一个会编造的答案。」

**要点**：一定要提到「按科目」「基于检索」「引用可核对」——这三个词是这个项目和"套壳 ChatGPT"的区别。

---

## 第 1 层：整体链路（必背，7 步）

用户提问 → 前端 `EventSource` 发 `GET /api/chat/stream?subjectCode=os&question=...`
→ ② `ChatController` 立刻返回 `SseEmitter`，把活丢给线程池
→ ③ `ChatService`：建会话 / 复用会话 → 用户提问落库 → 推 `meta` 事件
→ ④ `RetrievalService`：在该科目的切片里做全文检索，取 Top-5
→ ⑤ 拼 Prompt：系统提示词 + 5 段资料 + 最近 3 轮历史 + 当前问题
→ ⑥ `LlmClient` 调 DeepSeek（`stream=true`），每读到一块就 `onDelta` 推给前端
→ ⑦ 结束后推 `citations` + `done`，把回答和引用一起落库

## 第 2 层：四个会被追问的技术点

### Q1：为什么用 SSE，不用 WebSocket？

> 模型生成要几秒，等全部生成完再返回，用户会盯着白屏，所以要流式。
> 选 SSE 不选 WebSocket 是因为我们只需要**服务端单向推**，不需要双向通信。SSE 走普通 HTTP、不用协议升级、穿透代理方便，浏览器 `EventSource` 还自带断线重连。
> 代价是 `EventSource` 只能发 GET，所以问题放在 query 里传。

### Q2：中文检索为什么必须用 ngram？

> MySQL 默认分词器按空格和标点切词，中文句子会被当成一个整体词，搜「死锁」根本命中不了。加 `WITH PARSER ngram` 之后按 2-gram 切（死锁 / 锁的 / 的四…），中文才检索得动。
>
> 另外我用的是 `MATCH ... AGAINST` 而不是 `LIKE '%关键词%'`：LIKE 的前置通配符用不了索引，要全表扫描；而且它只判断"包不包含"，没有相关度，没法排序取 Top-K。`MATCH AGAINST` 走倒排索引，返回相关度分数，可以 `ORDER BY score DESC LIMIT 5`。

### Q3：为什么要把模型调用放到线程池？

> `LlmClient` 读大模型响应是阻塞的——要一直读到流结束。如果直接在 Controller 线程里做，几个并发就把 Tomcat 的线程池占满了，其他请求全部排队。所以 Controller 立刻返回 `SseEmitter`，真正的流式任务丢给一个固定大小线程池。

### Q4：怎么保证检索到的是对的资料？

> 检索 SQL 里强制 `WHERE subject_code = ?`，所以政治科目的提问不会捞到操作系统的片段。这一点我写了断言验证：在政治科目里问「死锁的四个必要条件」，返回的引用必须是政治资料，不能出现操作系统。

## 第 3 层：几个"为什么这么设计"

| 问题 | 回答 |
|---|---|
| 切多大一片？ | 400 字。太小上下文不完整，太大检索不精准还浪费 token |
| 为什么要有重叠？ | 80 字。防止一句话正好被切断，两边片段都不完整 |
| 怎么保证不编造？ | 两个手段：Prompt 里写死「只能依据资料回答，没有就说没有」；再把引用原文返回给用户核对 |
| 自动导入为什么幂等？ | 按「科目 + 标题」查重，否则每次重启重导一遍，库里几十份重复文档，检索结果全是重复片段 |
| 会话为什么单独建表？ | 复习是按科目反复追问的，要能切回历史对话；而且多轮对话要把上下文带进 Prompt |
| 前端为什么不打包？ | 一个页面 4 个组件，没有复杂模块图，用 Vite 的收益是 Tree-shaking 和 HMR，代价是装 Node、build、配 Nginx。现在前端由 Maven 打进 jar，一个 `java -jar` 就全起了 |

## 第 4 层：数字（被问到时能立刻报出来）

| 数字 | 含义 |
|---|---|
| 14 / 9 | 科目节点 14 个，其中 9 个可直接提问 |
| 5 | 每次检索取 Top-5 片段 |
| 400 / 80 | 切片大小 / 重叠字数 |
| 4 | SSE 事件类型：meta / delta / citations / done |
| 3 | 追问时带最近 3 轮历史 |
| 57 | 断言总数：接口 35 + 前端 22 |
| 666ms | 实测首字延迟（DeepSeek 真实调用） |

## 主动说的不足（比被问出来好）

> 「检索只做关键词，没做向量检索。语义相近但用词不同的问法会漏召回——比如问『怎么避免库存超卖』，资料里写的是『条件更新扣库存』，词面不匹配就查不到。要解决需要接 embedding 模型做向量召回，再和关键词做混合排序。
>
> 另外没有鉴权、没有限流。大模型是按 token 计费的，谁都能刷我的接口会造成费用损失。这两块我留了 TODO，思路是加 `HandlerInterceptor` 做简单鉴权 + 用 Redis 做滑动窗口限流。」

**这段特别重要**：它证明你知道边界在哪，而不是"做完了就完美了"。

## 一句话收尾（如果被问"这个项目你最大的收获"）

> 「最大的收获不是学会了调大模型接口，而是想清楚**检索质量决定了回答的上限**。模型再强，检索回来的资料不对，答案一定是错的。所以我花最多时间的是切分策略、ngram 索引、科目隔离这些'检索前置'的问题。」
